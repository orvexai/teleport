# Deployment Guide

> **Quick orientation.** Teleport is deployed in many shapes (Helm, Terraform/cloud, systemd, Docker, Teleport Cloud). This guide maps the *recipes shipped in this repo*. Operational deep dive lives in [`findings/build-deploy-ops.md`](./findings/build-deploy-ops.md). User-facing operator runbooks live at <https://goteleport.com/docs>.

---

## 1. Deployment Shapes

| Shape | What you get | Best for | Reference |
| --- | --- | --- | --- |
| **Teleport Cloud** | Hosted Auth + Proxy by Gravitational; you bring agents. | Teams that don't want to operate the control plane. | <https://goteleport.com/cloud> |
| **Helm — `teleport-cluster`** | A full Auth + Proxy cluster on Kubernetes. | Most self-hosted deployments. | `examples/chart/teleport-cluster/` |
| **Helm — `teleport-kube-agent`** | A Kubernetes-resident agent that registers SSH/app/db/kube services with an existing cluster. | Adding Kubernetes-access resources to a cluster. | `examples/chart/teleport-kube-agent/` |
| **Helm — `teleport-relay`** | A relay-node Helm release for the new transport layer. | Distributed relay topologies (RFD-driven; see `proto/teleport/relaytunnel/`). | `examples/chart/teleport-relay/` |
| **AWS Terraform — `starter-cluster`** | Single-AMI EC2 cluster with DynamoDB backend. | Demos and small POCs. | `examples/aws/terraform/starter-cluster/` |
| **AWS Terraform — `ha-autoscale-cluster`** | Multi-AZ HA cluster on EC2 + DynamoDB + S3 + ASG. | Production AWS. | `examples/aws/terraform/ha-autoscale-cluster/` |
| **systemd** | Single binary supervised by systemd (Linux). | Bare-metal / VM deployments. | `examples/systemd/` |
| **launchd** | Single binary supervised by launchd (macOS). | macOS daemons. | `examples/launchd/` |
| **Docker** | Containerised single binary. | Local dev, sidecars. | Distroless image at `build.assets/charts/Dockerfile-distroless` (production) |
| **Generic Terraform** | Standalone modules. | Custom infra. | `examples/terraform/`, `examples/terraform-starter/`, `integrations/terraform-modules/` |
| **Workload Clusters** | Multi-cluster setups for the new "Workload Clusters" feature. | Specialized routing. | `examples/workload-clusters/` |
| **Etcd cluster (recipe)** | Reference etcd deployment for the backend. | etcd-backed clusters. | `examples/etcd/` |
| **k8s-auth (recipe)** | Kubernetes-only authentication setup. | Specific k8s-only POCs. | `examples/k8s-auth/` |
| **Desktop registration (recipe)** | Windows desktop enrollment patterns. | Bootstrapping desktop access. | `examples/desktop-registration/` |
| **Grafana dashboards** | Sample Grafana dashboards for Prometheus metrics. | Monitoring. | `examples/grafana/` |
| **Athena event-store migration** | Migration helper from DynamoDB events → Athena. | Reducing audit-log query cost. | `examples/dynamoathenamigration/` + `examples/athena/` |
| **MCP-server examples** | Examples that verify Teleport-issued JWTs in MCP. | MCP integration projects. | `examples/mcp-servers/` |
| **Access-plugin minimal** | Skeleton for writing a new access plugin. | New integration projects. | `examples/access-plugin-minimal/` |

The umbrella `examples/README.md` indexes the recipes with one-liner descriptions.

## 2. Helm — `teleport-cluster`

The primary Kubernetes deployment.

```
examples/chart/teleport-cluster/
├── Chart.yaml
├── values.yaml                 Top-level configuration (auth/proxy/storage/…)
├── charts/                     Subcharts (operator, kube-agent, …)
├── templates/
│   ├── auth/                   Auth-service Deployment, Service, ConfigMap, RBAC, ServiceAccount
│   ├── proxy/                  Proxy Deployment, Service (LB), Ingress
│   ├── operator/               Embedded operator subchart (see below)
│   ├── network/                NetworkPolicies, ServiceMonitor
│   ├── secret/                 Secrets and Sealed-secrets shims
│   └── …
├── tests/                      helm-unittest tests (run via `make test-helm`)
└── README.md
```

Important `values.yaml` categories (read the file for the full set):

- `clusterName`, `proxyListenerMode`, `version`
- Storage backend selection (`dynamo`, `firestore`, `etcd`, `postgres`, `inmemory`)
- Audit event sink (`s3`, `dynamo`, `gcs`, `azureblob`, `postgres`, `firestore`, `athena`)
- TLS source (`acme`, `tls-secret`, `cert-manager`)
- HA replica counts
- Operator on/off (`operator.enabled`)
- Resources / requests / limits
- ServiceMonitor (Prometheus) on/off
- Pod disruption budgets, topology spread constraints

The chart is **canonical** for HA self-hosted deployments and is what `goteleport.com/docs/admin-guides/deploy-a-cluster/helm-deployments/` walks through.

Chart contributor conventions (`examples/chart/CONTRIBUTING.md`): every chart has `tests/` (helm-unittest cases), a `.lint/` folder for `chart-testing` configs, and `README.md` generated by `build.assets/tooling/cmd/render-helm-ref/`.

## 3. Helm — `teleport-kube-agent`

Agent-only Helm release. Registers SSH / Kubernetes / App / Database / Discovery services from inside a Kubernetes cluster against an external Teleport cluster.

```
examples/chart/teleport-kube-agent/
├── Chart.yaml
├── values.yaml                 roles: [kube,app,db,discovery,jamf,…]
├── templates/                  Per-role StatefulSet/Deployment
├── charts/                     Subcharts
├── tests/                      helm-unittest tests
```

`values.yaml` enables / disables roles and configures resource discovery rules.

---

## 4. Helm — Access Plugins

Each access plugin has a chart at `examples/chart/access/<plugin>/` (slack, jira, pagerduty, msteams, mattermost, discord, datadog, email). They are minimal: a Deployment + Secret + the plugin's config TOML.

Opsgenie and ServiceNow are absent — they're **Teleport Cloud-hosted** plugins (Gravitational runs the binary on the customer's behalf).

```
examples/chart/access/<plugin>/
├── Chart.yaml
├── values.yaml
├── templates/
│   ├── deployment.yaml
│   ├── secret.yaml
│   ├── service.yaml
└── tests/
```

## 5. Helm — `tbot` and SPIFFE

- `examples/chart/tbot/` — generic `tbot` Helm release. Renders the `tbot.yaml` config from values, mounts identity destinations, runs as a Deployment.
- `examples/chart/tbot-spiffe-daemon-set/` — `tbot` as a DaemonSet exposing SPIFFE SVIDs to other workloads on the node.

## 6. Helm — Event Handler

`examples/chart/event-handler/` deploys the audit-event forwarder (`integrations/event-handler/`). Sink is **Fluentd over mTLS**. Configure your destination on the Fluentd side; the chart wires up a Secret with the mTLS cert.

---

## 7. Helm — kube-agent-updater

`examples/chart/teleport-kube-updater/` deploys the agent updater (`integrations/kube-agent-updater/`). It watches deployed kube-agent releases and rolls them forward when a new version drops in the configured release channel.

## 8. AWS Terraform

Two flavours:

### 8a. Starter cluster (`examples/aws/terraform/starter-cluster/`)

Single AMI on EC2 with a self-contained Teleport cluster (Auth + Proxy + DB on the same instance). Backend: DynamoDB. Audit: DynamoDB. Sessions: S3.

### 8b. HA Autoscale cluster (`examples/aws/terraform/ha-autoscale-cluster/`)

Production-grade: separate Auth ASG + Proxy ASG, RDS for the cluster state (optional), DynamoDB for events/sessions in S3, NLBs in front of Proxy + Auth, ACM-issued TLS, IAM roles, KMS-backed cluster CA storage.

Both modules reference a Teleport AMI (built per release via Packer in a separate repo).

## 11. Release Flow

(From [`findings/build-deploy-ops.md` §8](./findings/build-deploy-ops.md).)

Teleport does **not** use `goreleaser`. The release chain is:

```
1. Engineer runs `make update-version` (bumps VERSION in Makefile)
                  `make update-tag`     (creates the git tag)
                  `make tag-build`      (dispatches build workflow)
                  `make tag-publish`    (dispatches publish workflow)
   The build/publish workflows actually live in the PRIVATE
   gravitational/teleport.e repo and are kicked off via
   `gh workflow run`.

2. Per-OS archives come from the `make release` family:
   release-unix, release-darwin, release-windows, release-connect.
   These run inside the buildbox so deps are pinned.

3. macOS builds go through `darwin-signing.mk` for codesigning +
   notarization. Windows uses PowerShell signing inside the workflow.

4. Helm chart versions are kept in sync by `make helm-version`
   (helm-janitor) which is invoked from `make setver`.

5. Audit-event docs are regenerated by
   `pnpm --filter=@gravitational/teleport event-reference`.

6. Preset roles are baked into `gen/preset-roles.json` by
   `build.assets/dump-preset-roles/`.
```

Container images are pushed to `public.ecr.aws/gravitational/teleport-distroless` (and friends) by the publish workflow.

## 12. Build Tags & FIPS

Build-tag matrix (auto-disabled by the Makefile where unsupported):

| Tag | Effect |
| --- | --- |
| `fips` | Switches Rust `rdpclient` → BoringSSL, sets `GOFIPS140=v1.0.0`, disables non-compliant code paths. Auto-disabled on arm64 unless cross-compile sysroot is set. |
| `bpf` | Compiles in eBPF session recording (Linux amd64/arm64 only). |
| `desktop_access_rdp` | Compiles in the CGo bridge to Rust RDP staticlib. |
| `pam` | PAM integration (libpam). |
| `libfido2`, `touchid`, `piv` | OS-specific hardware-key support. |
| `vnetdaemon` | VNet daemon support. |
| `sessionhelper_embed`, `webassets_embed` | Embed auxiliary binary / web assets in the main binary. |
| `grpcnotrace` | Disable gRPC tracing instrumentation (reduce binary size). |
| `kustomize_disable_go_plugin_support` | Reduce binary size by disabling kustomize Go plugins. |

## 13. Observability — Diagnostics in Deployment

Each `teleport` process can expose a diagnostics HTTP endpoint via the `--diag-addr` flag (`tool/teleport/common/teleport.go:173`). It serves:

- `/metrics` — Prometheus metrics (~150 metric names; see `metrics.go`)
- `/healthz`, `/readyz`
- `/debug/pprof/*`
- Log-level controls

Distributed tracing is configured via the `tracing_service` block in `teleport.yaml` (not a CLI flag). Consumed by `lib/observability/tracing/`. Reference: `examples/grafana/` for dashboard ideas.
